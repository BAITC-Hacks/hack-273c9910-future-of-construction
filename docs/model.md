# Модель и данные

Источник: синтетический датасет и подробные правила задания «Аким на 5 часов», предоставленные организаторами участнику. Ниже зафиксированы все входные значения для воспроизведения расчёта. Названия районов не означают, что значения отражают актуальную статистику Астаны.

## Ограничения сценария

- Единый бюджет: **100 условных единиц**. Валютного эквивалента нет; остаток не даёт бонуса.
- Ровно **5 решений**, каждое мероприятие выбирается максимум один раз.
- Не более **2 мер одного направления**. Допускается не охватить все пять направлений.
- Для районной меры требуется один существующий район. Для общегородской район указывать нельзя.
- Несовместимые меры запрещены. При любой ошибке официальный Score не вычисляется, возвращается причина.
- Порядок решений не влияет на основной результат. Все команды начинают с одинаковых значений.

Бюджет и правила находятся в [`src/domain/constants.ts`](../src/domain/constants.ts), валидатор — в [`src/engine/validator.ts`](../src/engine/validator.ts).

### Синергии и несовместимости

| Выбранная пара | Бонус |
|---|---|
| M1 + M2 | T1 +2 в районе M1 |
| M10 + M12 | B1 +2 в районе M10 |
| M5 + M6 | E2 +2 в районе M5 |

Бонус применяется один раз, **без масштабирования лагом**. «Район первой меры» означает закреплённую в правиле районную меру, а не очередность выбора в интерфейсе.

M1 и M3 запрещены вместе независимо от районов. M4 и M7 запрещены в одном районе. M5 и M13 также запрещены в одном районе. Правила находятся в [`synergies.ts`](../src/data/synergies.ts) и [`incompatibilities.ts`](../src/data/incompatibilities.ts).

## Алгоритм расчёта

1. Проверить все ограничения набора.
2. Для каждой меры вычислить коэффициент `(8 − L) / 8` и умножить её полные эффекты на него. Отрицательные эффекты масштабируются так же.
3. Суммировать эффекты мер и активные синергии для каждой пары «район × показатель».
4. Прибавить сумму к исходному значению, затем ограничить диапазоном `[0, 100]`.
5. Посчитать оценки районов, среднее по населению и критические пары, затем итоговый Score.

```text
I'_dk = clip(I_dk + Σ(effect_mk × (8 − L_m) / 8) + synergy_dk, 0, 100)
D_d = Σ(w_k × I'_dk)
D_avg = Σ(pop_d × D_d)
N_crit = число (d, k), для которых I'_dk < 40
Score = 0.7 × D_avg + 0.3 × min(D_d) − N_crit
```

`clip` выполняется после суммирования, поэтому перестановка решений не меняет результат. Промежуточные значения не округляются; округление используется только при отображении. Сам Score дополнительно не ограничивается: применяется формула из задания.

Оценка 30% за самый слабый район и штрафы объясняют, почему увеличение среднего показателя не всегда даёт лучший результат. Мера M11 показывает компромисс модели: улучшает B2, одновременно ухудшая T1.

## Контрольный расчёт

Базовый `D_avg = 56.8624`, минимум `D = 49.18`, критических пар — 2:

```text
0.7 × 56.8624 + 0.3 × 49.18 − 2 = 52.55768
```

Набор: **M7/Нура, M8/Нура, M10/Нура, M12/город, M5/Сарыарка**.

| Изменение | Расчёт | Итог |
|---|---|---:|
| Нура S1 | 38 + 16 × 5/8 | 48 |
| Нура S2 | 35 + 14 × 5/8 | 43.75 |
| Нура B1 | 55 + 12 × 7/8 + 2 | 67.5 |
| Нура B2 | 50 + 2 × 7/8 | 51.75 |
| Сарыарка E2 | 40 + 14 × 5/8 | 48.75 |
| Сарыарка C1 | 45 + 4 × 5/8 | 47.5 |
| C2 каждого района | Исходное значение + 5 × 7/8 | +4.375 |

После мер `D_avg = 58.0776`, самый слабый район — Нура с `D = 52.9625`, критических пар — 0:

```text
Score = 0.7 × 58.0776 + 0.3 × 52.9625 = 56.54307
Прирост = 56.54307 − 52.55768 = 3.98539
Стоимость = 24 + 20 + 12 + 14 + 25 = 95
Остаток = 100 − 95 = 5
```

Этот пример проверяется через реальный API командой `npm run smoke:model` после `npm run build`.

## Дополнительный режим событий

События — расширение проекта, не часть исходного контрольного примера. Базовые данные и бюджет 100 сохраняются. Событие задаёт отдельный резерв: `heating_main` — 8, `spring_flood` — 10, `storm` — 6. Доступный лимит равен `100 − reserve`, остаток — `лимит − стоимость мер`.

Сервер получает только ID события и сам определяет резерв по каталогу. Симуляция, валидация, советник и оптимизатор используют один лимит. Резерв сам по себе не улучшает показатели и не добавляет баллы. Для сравнения разных команд требуется одинаковое событие либо обычный режим без событий.

## Границы модели и роль AI

Модель линейно суммирует фиксированные эффекты, учитывая только перечисленные синергии и несовместимости. Она не моделирует вероятность срыва стройки, изменение населения, инфляцию и последующие расходы на содержание. Эти допущения позволяют независимо воспроизвести результат.

LLM получает уже рассчитанные значения до/после, дельты и вклады мер; её роль — объяснение. Числовой результат хранится отдельно от текста модели. При отсутствии ключа или ошибке провайдера используется явно обозначенный локальный анализ. Он не подменяет вызов LLM при оценке AI-интеграции.

Оптимизатор и поиск замен — алгоритмы над этой моделью. Их рекомендации проверены теми же ограничениями, но не являются доказательством полезности мер в реальном городе.
